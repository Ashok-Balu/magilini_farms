# Feature Inventory

Audit date: 2026-10-23

## Classification

1. Fully implemented and verified by tests
2. Implemented but not adequately tested
3. Partially implemented
4. Missing
5. Implemented with defects
6. Blocked by a business decision or external configuration

No feature qualifies as **1** because available tests are unit/component/controller tests with mocked data or providers; the repository has no database-backed customer/admin end-to-end workflow suite. Backend: 125 tests; frontend: 108 tests. A feature may be implemented and have focused tests while still being classified as **2** when meaningful integration behavior remains unverified.

## Customer Features

- **Home page and product discovery — 2.** Home and featured-product discovery are implemented; top-selling products are ranked by paid-order units sold. Automated view/controller tests exist, but no database-backed discovery workflow test verifies the aggregate against persisted orders. Evidence: [HomeView.vue](frontend/src/views/HomeView.vue); `getFeaturedProducts`, `getTopSellingProducts` in [productController.js](backend/src/controllers/productController.js).
- **Product search, filtering, sorting and pagination — 2.** Search, category/price filters, sorting and paging are wired through the shop UI and API. Price sorting uses the aggregate `lowestPrice` across variants; no database-backed test verifies filter/sort/page combinations against catalog records. Evidence: [ShopView.vue](frontend/src/views/ShopView.vue); `getProducts` in [productController.js](backend/src/controllers/productController.js).
- **Product details, images, pricing, units and stock — 2.** Product detail pages show images, variants, prices and stock; cart additions reject unavailable variants and transactional inventory reservation rechecks variant availability/stock before order creation. Image uploads depend on Cloudinary configuration. Evidence: [ProductView.vue](frontend/src/views/ProductView.vue); `addItem` in [stores/index.js](frontend/src/stores/index.js); `reserveInventory`, `placeOrder` in [inventoryService.js](backend/src/services/inventoryService.js), [orderController.js](backend/src/controllers/orderController.js); [Product.js](backend/src/models/Product.js).
- **Categories and seasonal availability — 2.** Public active categories, admin category CRUD and seasonal product states/notifications are implemented; no workflow tests cover them. Evidence: public `/categories` route in [routes/index.js](backend/src/routes/index.js); `adminCreateCategory`, `adminUpdateCategory`, `updateSeasonalStatus` in [miscController.js](backend/src/controllers/miscController.js) and [productController.js](backend/src/controllers/productController.js); [ShopView.vue](frontend/src/views/ShopView.vue).
- **Guest cart and persistent cart — 2.** Guests can add items, and the cart is stored in browser `localStorage`; no account/server-side cart exists, so persistence is browser-local. Evidence: `useCartStore`, `loadCart`, `saveCart` in [stores/index.js](frontend/src/stores/index.js); [App.vue](frontend/src/App.vue).
- **Cart updates and stale-cart reconciliation — 2.** Quantity changes/removal, stock caps and catalog refresh/reconciliation are implemented; unavailable/deleted variants are removed and quantities are capped to current stock. Reconciliation is browser/API tested but not verified against a live catalog database. Evidence: `updateQty`, `loadCart`, `reconcile` in [stores/index.js](frontend/src/stores/index.js); `placeOrder` in [orderController.js](backend/src/controllers/orderController.js).
- **Registration and email/password login — 2.** Customer registration, password hashing, login, cookies and rate limits are implemented and have controller/component tests; complete browser-to-database flows are unverified. Evidence: `register`, `login` in [authController.js](backend/src/controllers/authController.js); routes/validation in [routes/index.js](backend/src/routes/index.js); [RegisterView.vue](frontend/src/views/RegisterView.vue), [LoginView.vue](frontend/src/views/LoginView.vue).
- **Logout — 2.** The API clears the auth cookie and the frontend clears auth state; controller/component tests exist, but session behavior is not verified end-to-end. Evidence: `logout`, `clearAuthCookies` in [authController.js](backend/src/controllers/authController.js), [auth.js](backend/src/middleware/auth.js); `useAuthStore.logout` in [stores/index.js](frontend/src/stores/index.js).
- **Forgot password and reset password — 5.** Token creation, expiry and reset are implemented. In production, email delivery requires `EMAIL_USER`/`EMAIL_PASS`; without SMTP the message is only printed to the server console, while the endpoint still returns the generic “sent” response. Evidence: `forgotPassword`, `resetPassword` in [authController.js](backend/src/controllers/authController.js); `sendEmail`, `sendPasswordResetEmail` in [emailService.js](backend/src/services/email/emailService.js); [ForgotPasswordView.vue](frontend/src/views/ForgotPasswordView.vue), [ResetPasswordView.vue](frontend/src/views/ResetPasswordView.vue).
- **Customer profile and saved addresses — 2.** Profile and address CRUD/default selection are implemented behind customer authorization, but have no workflow tests. Evidence: `getProfile`, `updateProfile`, address handlers in [customerController.js](backend/src/controllers/customerController.js); [AccountView.vue](frontend/src/views/AccountView.vue).
- **Browser geolocation and reverse geocoding — 2.** Checkout requests browser geolocation and uses Nominatim reverse geocoding, then validates the resulting PIN. It depends on user permission, browser support and the public geocoding service; manual PIN entry is the fallback. Evidence: `useMyLocation` in [CheckoutView.vue](frontend/src/views/CheckoutView.vue).
- **Pincode validation and delivery serviceability — 2.** Six-digit PIN validation, admin PIN CRUD, serviceability overrides/reasons and postal-service lookup/cache are implemented. Resolving uncached PINs and real delivery estimates depend on the external postal service; the live integration is not workflow-tested. Evidence: `checkPincode`, `adminCreatePincode`, `adminUpdatePincode` in [miscController.js](backend/src/controllers/miscController.js), `getDeliveryByPincode` in [deliveryService.js](backend/src/services/deliveryService.js); [PincodesView.vue](frontend/src/views/admin/PincodesView.vue).
- **Delivery charges, minimum order and estimated delivery — 2.** Zone fees/estimates and serviceability are returned by `getDeliveryByPincode`; checkout loads `minimumOrderKg` from `/store-settings` and the backend enforces `MIN_ORDER_KG`. Configuration and geocoding/postal-service integration are not production-tested. Evidence: `getStoreSettings` in [miscController.js](backend/src/controllers/miscController.js); `getDeliveryByPincode`, `placeOrder` in [deliveryService.js](backend/src/services/deliveryService.js), [orderController.js](backend/src/controllers/orderController.js); `loadSettings`, `minMet` in [stores/index.js](frontend/src/stores/index.js), [CheckoutView.vue](frontend/src/views/CheckoutView.vue).
- **Checkout, order placement and payment — 6.** Idempotent order placement, transactional stock reservation, and Razorpay/direct-UPI/pay-at-farm flows are implemented. Razorpay requires provider credentials; direct UPI requires configured merchant details, and manual payments require admin confirmation. Provider execution/reconciliation cannot be verified without external configuration. Evidence: `placeOrder` in [orderController.js](backend/src/controllers/orderController.js); payment handlers in [paymentController.js](backend/src/controllers/paymentController.js); [razorpayService.js](backend/src/services/razorpayService.js), optional settings in [env.ts](backend/src/config/env.ts); [CheckoutView.vue](frontend/src/views/CheckoutView.vue).
- **Order history and order details — 2.** Authenticated customer order list/detail endpoints and account screens exist; not tested as a workflow. Evidence: `getMyOrders`, `getOrder` in [orderController.js](backend/src/controllers/orderController.js); [AccountView.vue](frontend/src/views/AccountView.vue), [OrderDetailView.vue](frontend/src/views/OrderDetailView.vue).
- **Order tracking and invoice downloads — 2.** Public tracking returns only operational status fields; invoice downloads require customer authentication and the order is scoped to the owner. Customer-account and admin invoice endpoints also exist. No authenticated end-to-end invoice workflow test runs against a database. Evidence: `trackOrder`, `trackOrderInvoice`, `downloadInvoice` in [orderController.js](backend/src/controllers/orderController.js); protected route in [routes/index.js](backend/src/routes/index.js); `generateInvoicePDF` in [invoiceService.js](backend/src/services/invoiceService.js); [TrackView.vue](frontend/src/views/TrackView.vue).
- **Order cancellation and refunds — 2.** Customer/admin cancellation validates legal status transitions and releases reserved stock; Razorpay refunds, manual refund confirmation, webhooks and reconciliation are implemented. Actual provider refunds and manual UPI refunds depend on external payment configuration/operations. Evidence: `cancelMyOrder`, `updateOrderStatus` in [orderController.js](backend/src/controllers/orderController.js); `processOrderRefundAdmin`, `getPaymentReconciliation` in [paymentController.js](backend/src/controllers/paymentController.js); [refundService.js](backend/src/services/refundService.js); [routes/index.js](backend/src/routes/index.js).
- **Coupons and discounts — 2.** Coupon validation and delivery/price discounts are reflected in checkout and order totals, including the remaining fee when a free-delivery coupon has a cap; order-time redemption limits are reserved transactionally. Database concurrency and UI total consistency are not covered by a multi-checkout integration test. Evidence: `applyCoupon` in [miscController.js](backend/src/controllers/miscController.js); coupon reservation and total calculation in `placeOrder` in [orderController.js](backend/src/controllers/orderController.js); `deliveryAmountDue`, `orderTotal` in [CheckoutView.vue](frontend/src/views/CheckoutView.vue).
- **Product reviews and ratings — 2.** Public review submission/listing and ratings aggregates are present; no customer review workflow tests exist. Evidence: `getProductReviews`, `submitReview` in [miscController.js](backend/src/controllers/miscController.js); [ProductView.vue](frontend/src/views/ProductView.vue).
- **Complaints and customer support — 2.** Customer complaint submission, photo upload, order ownership/delivery checks, a 24-hour window and admin resolution UI are implemented; no workflow tests. Evidence: `submitComplaint`, `getMyComplaints`, `adminUpdateComplaint` in [miscController.js](backend/src/controllers/miscController.js); [ComplaintView.vue](frontend/src/views/ComplaintView.vue), [ComplaintsView.vue](frontend/src/views/admin/ComplaintsView.vue).
- **Bulk orders and enquiries — 2.** Enquiry submission and admin status handling are implemented, but the route has no dedicated request schema and the flow is untested. Evidence: `submitBulkEnquiry`, `adminUpdateBulkEnquiry` in [miscController.js](backend/src/controllers/miscController.js); [BulkView.vue](frontend/src/views/BulkView.vue), [BulkEnquiriesView.vue](frontend/src/views/admin/BulkEnquiriesView.vue).

## Verification

- `backend`: `npm.cmd test` passed all 125 tests after notification delivery history/retry and audit history were added; backend build passed. No production database is configured.
- `frontend`: `npm.cmd test` passed all 108 tests and the Vite production build passed after notification and audit-history UI changes. Existing build warning: Pinia store is both statically and dynamically imported.
- No database-backed API tests, browser workflow tests or configured third-party integration tests were run. Razorpay, SMTP, Cloudinary, WhatsApp and postal-service behavior therefore remains configuration/integration dependent.
